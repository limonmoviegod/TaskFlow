# Звіт до лабораторної роботи №1

**Тема:** Технічне завдання, вибір моделі життєвого циклу, визначення версій, розробка шаблонів
**Проєкт:** TaskFlow — REST API для управління завданнями

## 1. Хід роботи
1. **ТЗ.** Складено технічне завдання за шаблоном із 11 розділів (`TЗ.md`): п'ять функціональних вимог із
   критеріями приймання, нефункціональні вимоги, архітектура та план із двох ітерацій і релізу.
2. **Модель життєвого циклу.** Обрано Scrum зі спринтом 1 тиждень. Обґрунтування, ризики, артефакти
   (backlog, DoD) та розклад подій — у `LIFECYCLE.md`.
3. **Версіонування.** Запроваджено SemVer (MAJOR.MINOR.PATCH) і спрощений GitFlow
   (`main`, `develop`, `feature/*`, `release/*`, `hotfix/*`) із Conventional Commits (`VERSIONING.md`).
4. **Шаблони.** Створено `RELEASE_TEMPLATE.md`, `CHANGELOG.md`, `ACCEPTANCE_CHECKLIST.md`.
5. **Демонстрація Git.** Реалізовано дві feature-гілки та реліз:
   - `feature/add-tasks-api` → merge у `develop` (`--no-ff`);
   - `feature/task-filter-and-done` → merge у `develop` (`--no-ff`);
   - `release/1.0.0` → merge у `main`, тег `v1.0.0`, зворотний merge у `develop`.
6. **Автоматизація.** Додано GitHub Actions: тести на push/PR, створення релізу з архівом при пуші тегу `v*`.

## 3. Висновки
- Чітко записане ТЗ з критеріями приймання одразу перетворюється на тест-кейси та чекліст готовності фічі.
- Для малої команди Scrum із короткими спринтами дає регулярні робочі інкременти й добре поєднується з CI.
- SemVer разом із Conventional Commits робить зміст релізу передбачуваним: тип коміту визначає, яка частина версії зміниться.
- Гілки `feature/*` з `merge --no-ff` зберігають у історії межі кожної фічі, а теги й `CHANGELOG.md` слугують єдиним джерелом правди про релізи.
- Автоматизація (CI + автореліз) зменшує ручну роботу та ризик помилки під час випуску.
