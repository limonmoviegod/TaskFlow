# Технічне завдання: TaskFlow

## 1. Вступ
TaskFlow — невеликий вебсервіс (REST API) для ведення списку завдань у малих командах.
Він дозволяє створювати завдання, відмічати їх виконаними та фільтрувати за статусом.

## 2. Мета і задачі
- **Мета:** створити простий, добре протестований і версіонований сервіс управління завданнями, який можна розгорнути за одну команду.
- **Основні задачі:**
  - реалізувати REST API для створення, перегляду та завершення завдань;
  - забезпечити автоматичне тестування та CI;
  - запровадити політику версій (SemVer) і Git-стратегію (спрощений GitFlow);
  - підготувати документацію та шаблони релізів.

## 3. Цільова аудиторія
- **Розробники малих команд (2–10 осіб)** — інтегрують API у власні інструменти.
- **Студенти / учасники навчальних проєктів** — ведуть список задач проєкту.

Ключові сценарії:
1. Користувач додає нове завдання з назвою.
2. Користувач переглядає всі завдання або лише невиконані.
3. Користувач відмічає завдання виконаним.
4. Адміністратор перевіряє працездатність сервісу (`/health`).

## 4. Функціональні вимоги
| № | Функція | Опис | Критерії приймання |
|---|---------|------|--------------------|
| F1 | Перевірка стану | `GET /health` повертає статус і версію | Відповідь 200, JSON `{"status":"ok","version":"X.Y.Z"}` |
| F2 | Створення завдання | `POST /tasks` з полем `title` | 201 і об'єкт із `id`, `title`, `done=false`; порожній `title` → 400 |
| F3 | Список завдань | `GET /tasks` | 200 і масив усіх завдань |
| F4 | Фільтрація | `GET /tasks?done=true\|false` | Повертаються лише завдання з відповідним статусом |
| F5 | Завершення завдання | `PATCH /tasks/<id>/done` | 200 і `done=true`; неіснуючий id → 404 |

## 5. Нефункціональні вимоги
- **Продуктивність:** час відповіді будь-якого ендпоінта < 200 мс при 50 одночасних запитах.
- **Безпека:** валідація вхідних даних; у наступних версіях — авторизація OAuth2 (поза обсягом v1.0.0).
- **Сумісність:** Python 3.10+; Linux, macOS, Windows; будь-який HTTP-клієнт.
- **Логування/моніторинг:** логи запитів у stdout; ендпоінт `/health` для моніторингу.
- **Якість коду:** покриття юніт-тестами ≥ 80 %.

## 6. Обмеження та припущення
- Технології: Python, Flask, pytest, GitHub Actions.
- У v1.0.0 дані зберігаються в пам'яті процесу (без БД); персистентність — у v1.1.0.
- Команда: 1 розробник; термін — 3 тижні.
- Автентифікація в v1.0.0 відсутня (припущення: сервіс працює у довіреній мережі).

## 7. Інтерфейс користувача (коротко)
Інтерфейс — HTTP API. Мікро-флоу:

```
Клієнт --POST /tasks {"title":"Написати звіт"}--> Сервіс --201 {id:1,done:false}--> Клієнт
Клієнт --GET /tasks?done=false--> Сервіс --200 [{id:1,...}]--> Клієнт
Клієнт --PATCH /tasks/1/done--> Сервіс --200 {id:1,done:true}--> Клієнт
```

## 8. Архітектурні рішення (високорівневі)
- **Сервер:** Flask-застосунок (application factory `create_app`), Blueprint `tasks`.
- **Сховище:** in-memory (v1.0.0) → SQLite/PostgreSQL (v1.1.0).
- **CI/CD:** GitHub Actions — тести на кожен push/PR; на push тегу `v*` — створення релізу з артефактом.
- **Деплой:** `pip install -r requirements.txt && flask --app app run`; у перспективі Docker.

## 9. План робіт та етапи
- **Ітерація 1 (13.10–19.10):** каркас проєкту, `/health`, ендпоінти `POST/GET /tasks`, тести.
- **Ітерація 2 (20.10–26.10):** фільтрація, `PATCH /tasks/<id>/done`, CI, документація.
- **Реліз 1 (27.10):** гілка `release/1.0.0`, оновлення CHANGELOG, тег `v1.0.0`.

## 10. Критерії приймання

| ID | Крок | Очікуваний результат |
|----|------|----------------------|
| TC1 | `GET /health` | 200, `status=ok` |
