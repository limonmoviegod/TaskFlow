# Вибір моделі життєвого циклу

## Обрана модель: Agile (Scrum) + спрощений GitFlow + CI

### Чому підходить
Проєкт малий, вимоги можуть уточнюватися в процесі, команда — 1–2 особи, а термін короткий (3 тижні).
Scrum дає короткі цикли зворотного зв'язку: після кожного спринту є робоча, протестована версія.
Waterfall тут невиправданий: він передбачає повну фіксацію вимог наперед і пізнє тестування,
що збільшує ризик знайти проблеми лише наприкінці. V-model надто формальна для такого обсягу.
Scrum добре поєднується з CI та SemVer: кожен спринт завершується інкрементом, який можна позначити версією.

### Переваги й недоліки
| Переваги | Недоліки |
|----------|----------|
| Швидкий зворотний зв'язок, гнучкість до змін | Потрібна дисципліна ритуалів (planning, review, retro) |
| Робочий інкремент після кожного спринту | Складніше точно спланувати обсяг на весь проєкт |
| Добре сумісний з CI/CD і частими релізами | Для 1 людини частина ролей (PO, SM) збігається |

### Ризики
- **Розповзання вимог (scope creep)** → чіткий backlog і Definition of Done.
- **Недооцінка трудомісткості** → декомпозиція задач ≤ 1 дня.
- **Регресії** → автотести в CI на кожен push/PR.

### Артефакти
- **Product Backlog** — впорядкований список user stories (F1–F5 із ТЗ + побажання на майбутнє).
- **Sprint Backlog** — задачі, обрані на поточний спринт.
- **Increment** — працююча версія, позначена тегом.
- **Definition of Done:** код відповідає ТЗ; юніт-тести пройдено; code review проведено;
  API задокументовано; CHANGELOG оновлено; CI зелений.

### Розклад ітерацій
| Подія | Параметри |
|-------|-----------|
| Довжина спринту | 1 тиждень |
| Sprint Planning | понеділок, 30 хв |
| Daily (для 1 особи — запис у журналі) | щодня, 5 хв |
| Sprint Review | неділя, 30 хв, демо інкременту |
| Retrospective | неділя, 20 хв: що добре / що покращити / дії |
